# Git workflow and how it is enforced

The PRD (§10–§11) grades the Git history itself. These rules are therefore enforced by tooling, not left
to memory. The reasoning is recorded in ADR-011.

## Branch model

| Branch | Purpose | Changes by |
|---|---|---|
| `master` | Integrated, working code | Merged pull requests only (merge commits, never squash/rebase) |
| `feature/<kebab-name>` | One logical feature (plan §19.2) | Incremental commits; branched from `master` |
| `fix/<kebab-name>` | A focused fix | PR into `master` or `pre-release` |
| `pre-release` | Integration fixes, docs, deployment checks after the MVP is integrated | Direct commits allowed; merged back to `master` by PR |
| `release/vX.Y.Z` | The shipped version (video + deployment point here) | Cut from `pre-release`; frozen afterwards |
| tag `vX.Y.Z` | Marks the release commit | Created once, never moved or deleted |

Allowed pull requests: `feature/* → master` · `fix/* → master | pre-release` · `pre-release → master`.

## Commit messages

`<type>(<scope>): <description>` — types exactly as in the PRD: `feat fix refactor test docs chore build`
(CI changes use `build(ci)`). Scope is lowercase kebab-case. Description starts with a lowercase verb,
has at least three words, no trailing period, header ≤ 72 characters, and none of the words the PRD calls
out (`final`, `latest`, `wip`, `asdf`, `misc`, …). Merge and revert messages generated by Git/GitHub are
accepted as-is.

Accepted: `feat(pool): enforce Bullet's seat capacity` · `fix(pool): prevent overbooking available seats`.
Rejected: `update` · `feat(api): stuff` · `ci: add workflow` · `feat(auth): Add login.`

## Enforcement layers

| Layer | Where | Catches | Can be bypassed? |
|---|---|---|---|
| 1. Claude Code guardrails | `.claude/settings.json` deny rules + `.claude/hooks/guard-git.mjs` | Agent pushing, merging, rebasing, tagging, changing git config, skipping hooks, editing policy files, reading `.env` | Yes (unusual command spellings) — it's a seatbelt |
| 2. Local Git hooks | `.githooks/` + `scripts/git/policy.sh` | Bad commit messages, commits on `master`/`release/*`, bad branch names, `.env`/PRD/keys, secret-shaped strings, oversized commits (> 400 lines excl. lockfiles, migrations, Markdown), force pushes, direct pushes to `master`, deleting long-lived branches, malformed tags, pushing code that fails `npm run verify` | Yes (`--no-verify`) — fast feedback |
| 3. CI `git-policy` workflow | `.github/workflows/git-policy.yml` + `scripts/git/check-pr.sh` | Same message/file/secret rules on every PR and push, plus allowed source→target branch pairs | No, once it is a required status check |
| 4. GitHub rulesets | Repository settings | Direct pushes, force pushes and deletions on `master`/`pre-release`/`release/**`; merging without passing checks; tag tampering | No (bypass list left empty) |
| 5. Audit | `scripts/git/audit.sh` | Missing branches/tag, direct commits on `master`, bad messages anywhere in history, secrets ever committed, multiple author identities, suspicious branch sizes | Report only — run before submission |

Layers 3 and 4 are the enforcement; 1 and 2 exist so mistakes are caught in seconds instead of in a PR.

## One-time setup

Local (every clone): `git config core.hooksPath .githooks` (also run automatically by `npm install`
through the `prepare` script once `package.json` exists).

GitHub → **Settings → General → Pull Requests**: allow merge commits ✔, allow squash merging ✘, allow
rebase merging ✘, automatically delete head branches ✘ (evaluators inspect feature branches).

GitHub → **Settings → Rules → Rulesets** (available on public repositories with GitHub Free). Create after
the first PR has run `git-policy` once, so the check can be selected. Leave every bypass list empty.

| Ruleset | Target | Rules |
|---|---|---|
| `master` | Default branch | Restrict deletions · Block force pushes · Require a pull request before merging (0 approvals, allowed merge method: **Merge**) · Require status checks: `git-policy` (add `ci` after Session 1). Do **not** enable "Require linear history" — it forbids merge commits. |
| `long-lived` | `pre-release`, `release/**` | Restrict deletions · Block force pushes |
| `release-freeze` | `release/**` | Restrict updates (the branch can be created, never changed) |
| `release-tags` | Tags `v*` | Restrict deletions · Restrict updates · Block force pushes |

## Day-to-day flow

1. `git switch master && git pull` → `git switch -c feature/<name>`.
2. Commit in logical steps (hooks check each one). `git push -u origin feature/<name>`.
3. Open a PR into `master` using the template (traceability to plan sections, tests, AI usage).
4. `git-policy` and `ci` must pass → **Create a merge commit**. Keep the branch.
5. `git switch master && git pull`.

Release: `git switch -c pre-release master` → fixes/docs/deploy directly on `pre-release` → PR
`pre-release → master` → `git switch -c release/v1.0.0 pre-release` → push → `git tag -a v1.0.0` → push tag
→ `scripts/git/audit.sh`.
