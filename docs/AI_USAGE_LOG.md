# AI Usage Log

Written by me as I go, so the README's AI Usage section reflects what actually happened.
One row per meaningful suggestion. "Decision" is Accepted / Modified / Rejected.

| Date | Tool | Task | Suggestion | Decision | Why (in my own words) |
|---|---|---|---|---|---|
| 2026-09-25 | Claude (claude.ai) | Read PRD, produced implementation plan | Modular monolith, Postgres row locks + CHECK constraint for seat capacity, integer paisa, fare discount decided at trip start | Accepted | This is a small MVP with one obvious hot path (seat capacity) — microservices would add deployment and consistency overhead the PRD's own "don't over-engineer" note (§9) warns against. Row locks + a CHECK backstop is the standard, defensible way to make overbooking impossible at the database level, and integer paisa avoids float rounding bugs in money — all things I'd have specified myself, so I kept them as proposed. |
| 2026-09-25 | Review feedback + Claude | Plan revision 2 | Polling/retry policy for free-tier cold starts; single typed write path for status + history | Accepted | Free-tier hosts (Render, Neon) sleep between requests, so a naive fetch-on-mount would show a false "server down" error on the first request after idle — the backoff/cold-start handling in `apps/web/src/lib/polling.ts` fixes that directly. The single write-path-per-aggregate rule (`domain-writes/`) was the more important one: it's what makes it structurally impossible for a status update to skip writing its own history row, which several PRD-graded invariants depend on. |
| 2026-09-25 | Claude (claude.ai) | Free-tier hosting check | Neon instead of Render Postgres (30-day expiry); `Cache-Control: no-store` behind Netlify proxy | Accepted | Render's free Postgres tier deletes the database after 30 days of inactivity — a real risk for a project graded weeks after submission. Neon's free tier has no such expiry. The no-store header matters because Netlify's CDN would otherwise cache an API response meant for one specific signed-in user. |
| 2026-09-27 | Claude Code | Frontend redesign, round 2 | Two options put to me directly: (1) keep the dark "Electric Night" theme already merged, or switch to a light theme; (2) a purely abstract zone diagram, or a real basemap with zone pins | Rejected the first option in each pair, chose the alternative | Every real ride-pooling app I could think of (Uber, Pathao, Lyft, Grab) is light-primary, and the PRD's own story happens at 8:41 AM daytime — a dark cockpit theme reads as a generic "AI dashboard" look I explicitly didn't want. For the map: the backend only ever knows an abstract 10-zone grid, no real GPS — a live-looking map would misrepresent what the system actually does, which is exactly the kind of thing an evaluator is primed to probe. Recorded as [ADR-017](decisions/ADR-017-frontend-redesign-light-theme.md) and [ADR-018](decisions/ADR-018-frontend-map-real-basemap.md). |
| 2026-09-27 | Claude Code | Admin panel scope | Proposed alternative: let an admin force-cancel the ride/pool blocking a suspension, so the suspension takes effect immediately instead of being refused | Rejected | That would mean adding a new actor to the ride and pool state machines and their concurrency test suite — the most heavily-tested, most heavily-graded part of this codebase — just for an operator convenience the MVP doesn't need. Refusing with a clear `409` and waiting for the ride to finish keeps that code untouched. Recorded as [ADR-019](decisions/ADR-019-admin-panel-scope.md). |
